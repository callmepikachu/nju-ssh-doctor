## 根因

1. **直接原因**：beyond tunnel 的中转节点 `43.242.74.145:51820` 从 macmini 不可达（被墙或过载）。客户端 API 下发的 4 个「不同地区」节点实际是同一个 IP，无法通过换节点规避。
2. **放大原因**：beyond 客户端在节点不可达时**不会自动 fallback、也不会报错**，继续维持 `utun4` 存在、状态显示「已连接」的假象。所以表面上是「能连上但连不通」，极难定位。
3. **次要原因**：App 重启后隧道子进程依赖 sudo-prompt 拉起，若无人确认就会陷入 `隧道进程未运行` 状态。

## 修复

- 临时：QuickFox 作为 beyond 的底层出口（绕开对节点 IP 的直连）。
- 判定：`bin/doctor.sh` 按状态自动区分 A/B 类故障，A 类自动启 QuickFox，B 类提示重启 App。
- 长期：向 beyond 反馈「多节点同 IP + 无 fallback」；考虑把 frp / 自建反向隧道作为冗余通道。

## 经验教训

1. **排查顺序**：先看进程活着没 → 再看网卡在不在 → 再看路由在不在 → 最后才怀疑工具选错。本次第一轮把 `utun4` 误判为 Tailscale，就是跳过了「看进程」这一步。
2. **「能 ping 通自己」是基础检查**：`ping 100.64.0.249` 超时说明整条隧道已经哑了，此时再看上层目标毫无意义。
3. **日志要看出「静默」**：进程活着 ≠ 在工作。日志里 20:36 到 22:34 一条记录都没有，这本身就是最强的证据。
4. **两个工具叠加时，分清谁是「底层出口」**：QuickFox 不是并与 beyond 平行的第二层 VPN，而是它的传输层。
